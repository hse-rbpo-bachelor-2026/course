# Учебный кейс: сервис бронирования оборудования лаборатории

Это первая часть сквозного кейса **Lab Booking — сервис бронирования оборудования учебной лаборатории**, который используется на S01–S04. На S01 рассматриваются только продукт, пользователи, сценарии и объём. Необходимые для следующих занятий уточнения будут открываться постепенно.

Его задача — показать, **какого уровня конкретности достаточно для выбора и первичного ограничения командного проекта**.

Не нужно превращать этот кейс в полный проект или заранее применять к нему методы следующих занятий.

## Ситуация

Учебная лаборатория выдаёт студентам оборудование для самостоятельной работы: одноплатные компьютеры, наборы датчиков, камеры, микроконтроллеры и другие устройства.

Сейчас информация о доступности оборудования ведётся вручную, поэтому возникают накладки: два человека могут рассчитывать на одно устройство, часть оборудования временно недоступна, а отменённые бронирования не всегда учитываются вовремя.

Нужен небольшой сервис, через который студенты смогут посмотреть оборудование и забронировать его на определённое время.

Сотрудник лаборатории должен иметь возможность управлять состоянием оборудования и при необходимости отменять бронирования.

## Пользователи

### Студент

Студент может:

- просматривать оборудование;
- видеть, когда оборудование доступно;
- создавать собственные бронирования;
- просматривать свои бронирования;
- отменять собственные бронирования.

### Сотрудник лаборатории

Сотрудник лаборатории может:

- просматривать оборудование и бронирования;
- изменять состояние оборудования;
- при необходимости отменять бронирования.

## Основные сценарии

### Сценарий 1. Забронировать оборудование

Студент выбирает устройство, указывает желаемое время и создаёт бронирование.

После успешного действия выбранное оборудование считается занятым на этот интервал.

### Сценарий 2. Отменить бронирование

Студент просматривает свои активные бронирования и отменяет одно из них.

После отмены соответствующий интервал снова может стать доступным.

### Сценарий 3. Изменить состояние оборудования

Сотрудник лаборатории переводит оборудование, например, из состояния «доступно» в состояние «на обслуживании».

Оборудование, которое временно недоступно, не должно предлагаться для новых бронирований.

## Значимые объекты

Для продукта как минимум важны два типа объектов.

### Оборудование

Для каждого устройства нужно хранить, например:

- идентификатор;
- название;
- тип;
- текущее состояние.

Примеры состояний:

- доступно;
- на обслуживании;
- выведено из эксплуатации.

### Бронирование

Для бронирования нужно хранить, например:

- какое оборудование забронировано;
- кем;
- начало интервала;
- конец интервала;
- текущее состояние бронирования.

## Предполагаемый объём продукта

Для учебного проекта достаточно небольшого серверного приложения или веб-API.

Не требуется заранее делать:

- полноценный пользовательский интерфейс;
- мобильное приложение;
- интеграцию с университетскими системами;
- оплату и штрафы;
- систему уведомлений;
- физическую выдачу оборудования;
- сложную регистрацию пользователей.

Главное — чтобы основные сценарии работали, состояние сохранялось, а различия между действиями пользователей действительно существовали в логике приложения.

## Вопросы для обсуждения

Обсудите кейс в команде и подготовьте короткие ответы.

### 1. Какой здесь законченный пользовательский сценарий?

Выберите один сценарий и сформулируйте его как:

> потребность пользователя → основные действия → значимый результат

### 2. Чем реально различаются возможности пользователей?

Недостаточно сказать, что существуют роли «студент» и «сотрудник».

Назовите конкретные действия, которые одному пользователю разрешены, а другому — нет.

### 3. Какие два типа данных или объектов имеют разные последствия нарушения?

Выберите, например:

- бронирования;
- состояние оборудования.

Объясните, что конкретно произойдёт, если соответствующие данные будут неправильно изменены, удалены или станут недоступны.

### 4. Что можно убрать, не разрушив проект?

Представьте, что времени осталось мало.

Какие функции можно исключить, чтобы продукт всё ещё:

- имел собственную серверную логику;
- поддерживал не менее двух содержательных сценариев;
- различал возможности пользователей;
- работал с изменяемым состоянием;
- оставался пригодным для дальнейшей работы на курсе?

## Что здесь пока не требуется

На S01 для этого кейса не нужно:

- формулировать требования безопасности;
- строить модель угроз;
- выбирать средства защиты;
- проектировать CI;
- выбирать SAST, SCA или DAST;
- описывать проектные решения;
- строить трассировку;
- писать код.

Сейчас важен только сам объект: **что это за продукт, кто им пользуется, какие действия в нём действительно значимы и какой минимальный объём имеет смысл реализовывать**.
