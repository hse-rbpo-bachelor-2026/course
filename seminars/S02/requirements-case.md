# Учебный кейс: требования безопасности для сервиса бронирования оборудования

Это вторая часть сквозного **Lab Booking**. Предметное описание впервые разобрано на [S01](../S01/project-calibration-case.md); необходимый контекст повторён ниже.

На S02 вы учитесь отличать предметное правило от защитного свойства и формулировать **требования безопасности с критериями приёмки**. Не каждое правило становится `SR-*`.

Не нужно строить модель угроз или предлагать проектные решения — это будет позже.

## 1. Контекст продукта

Учебная лаборатория выдаёт студентам оборудование для самостоятельной работы.

Сервис позволяет:

- просматривать оборудование;
- создавать бронирования;
- просматривать и отменять собственные бронирования;
- сотруднику лаборатории — изменять состояние оборудования;
- сотруднику лаборатории — при необходимости отменять бронирования.

Основные объекты:

- оборудование;
- бронирование;
- пользователь.

## 2. Уточнённые правила продукта

На S02 считаем, что для продукта действуют следующие правила.

### 2.1. Собственные бронирования

Обычный студент может отменять только собственные бронирования.

Наличие идентификатора чужого бронирования само по себе не даёт права управлять им.

### 2.2. Владелец бронирования

Бронирование создаётся от имени действующего пользователя. Студент не может оформить его от имени другого пользователя. Как именно это обеспечивается в реализации, на S02 выбирать не требуется.

### 2.3. Состояние оборудования

Изменять состояние оборудования может только сотрудник лаборатории.

Обычный студент не должен получать это право даже при прямом обращении к соответствующей операции API.

### 2.4. Недоступное оборудование

Оборудование в состоянии:

- `maintenance`;
- `retired`

не должно быть доступно для создания нового бронирования.

### 2.5. Пересекающиеся бронирования

Для одного устройства не должно существовать двух активных бронирований с пересекающимися интервалами.

### 2.6. Временной интервал

Для нового бронирования:

- начало должно быть раньше окончания;
- продолжительность не должна превышать четырёх часов.

Некорректный запрос не должен изменять состояние системы.

### 2.7. Привилегированная отмена

Сотрудник лаборатории может отменить чужое активное бронирование.

При таком действии необходимо указать причину отмены.

После выполнения должно быть возможно установить:

- кто выполнил действие;
- какое бронирование было затронуто;
- когда это произошло;
- какая причина была указана.

## 3. Калибровка: правило, требование и критерий приёмки

**Предметное правило** задаёт порядок работы продукта. **Требование безопасности** описывает значимое защитное свойство. **Критерий приёмки** определяет наблюдаемый результат, по которому можно решить, выполнено ли требование. Проверяемость необходима для SR, но сама по себе не отличает безопасность от обычной функциональности.

Короткий пример на другом продукте — сервисе личных черновиков:

- Предметное правило: название черновика должно содержать от 1 до 80 символов.
- Само по себе ограничение длины ещё не объясняет защитное свойство; автоматически назначать ему `SR-*` не нужно.
- Защитное свойство: пользователь не должен изменять личные черновики другого пользователя.
- **SR-EXAMPLE. Требование:** система допускает изменение личного черновика только его владельцем.
- **Критерий приёмки:** при попытке пользователя B изменить черновик пользователя A действие отклоняется, а содержимое и владелец черновика остаются прежними; владелец A может выполнить допустимое изменение своего черновика.

`SR-EXAMPLE` — учебное обозначение только для этого разбора. Его не нужно переносить в Lab Booking или собственный проект. Пример показывает требуемую конкретность; он не определяет механизм реализации и не утверждает, что тест уже выполнен.

Сравните с фразами «система должна быть защищённой», «нужна безопасная авторизация», «валидировать все данные». Из них нельзя однозначно восстановить ситуацию, обязательное поведение и наблюдаемый результат.

Для бизнес-правил о времени или состоянии связь с безопасностью зависит от контекста. Объясните, какое значимое свойство защищается и к каким последствиям приводит нарушение. Если такого обоснования нет, правило остаётся предметным ограничением. Модель угроз на этом этапе не требуется.

## 4. Задание 1. Выберите и сформулируйте требования безопасности

Для правил из раздела 2 сначала обсудите:

1. Что правило означает для обычной работы продукта?
2. Какое значимое защитное свойство может быть с ним связано?
3. Достаточно ли контекста для такого вывода? Если нужны допущения, какие именно?

Затем сформулируйте требования только для обоснованных защитных свойств. Обычные предметные правила не удаляются из продукта, но не обязаны получать `SR-*`. Допускаются разные обоснованные наборы; не нужно превращать каждое правило в отдельную строку безопасности.

Для требования должно быть понятно, какое поведение обязательно и в каких условиях. Не выбирайте библиотеку или механизм защиты вместо формулировки свойства.

## 5. Задание 2. Добавьте критерий приёмки

Для каждого `SR-*` укажите ситуацию и ожидаемый наблюдаемый результат. Критерий отвечает на вопрос:

> Как можно определить, что требование выполняется?

Там, где существенна попытка изменить состояние, уточните, что должно остаться неизменным при отказе. Учитывайте допустимое действие законного пользователя, если оно нужно для понимания свойства.

Готовый тест, код или технический стенд сейчас не требуются. «Проверить права доступа» недостаточно: это название действия без условий и ожидаемого результата.

## 6. Задание 3. Назначьте устойчивые идентификаторы

Используйте короткие стабильные идентификаторы:

```text
SR-01
SR-02
SR-03
...
```

Идентификатор нужен не ради оформления.

На следующих занятиях по нему будут связываться:

- угрозы;
- проектные решения;
- будущие проверки.

После присвоения идентификатор не следует менять без необходимости.

## 7. Задание 4. Найдите избыточность

После составления требований проверьте:

- не повторяют ли два требования одно и то же;
- нет ли требований, которые описывают конкретную технологию вместо свойства продукта;
- можно ли реально проверить каждое требование;
- относится ли требование именно к этому продукту;
- не появилось ли требование только потому, что «так обычно пишут про безопасность».

Если два требования описывают одно свойство, лучше объединить их.

## 8. Вопросы для общего разбора

Подготовьтесь коротко объяснить:

1. Какое из требований оказалось сложнее всего сформулировать проверяемо?
2. Почему не каждое предметное правило получило `SR-*`?
3. Почему фраза «проверять права доступа» слабее конкретного критерия приёмки?
4. Нужно ли уже сейчас знать точную реализацию требования?
5. Какие требования из вашего списка могут оказаться связанными между собой?

## 9. Что сохранить для следующего занятия

Сохраните свой рабочий набор учебных `SR-*` с критериями приёмки и существенными допущениями в удобных заметках. На S03 вы продолжите именно этот набор; номера требований разных команд могут различаться. Отдельная сдача заметок или новый обязательный файл в проекте не нужны. В проектный репозиторий сохраняются требования собственного продукта, а не Lab Booking.

## 10. Что пока не требуется

На S02 для этого кейса не нужно:

- строить модель угроз;
- перечислять атаки;
- выбирать конкретные библиотеки и механизмы реализации;
- писать проектные решения;
- строить цепочку `угроза → требование → решение`;
- создавать `CONTRIBUTIONS.md`;
- писать код специально для учебного кейса.

Сейчас задача одна:

> **получить небольшой набор требований безопасности с обоснованными защитными свойствами и конкретными критериями приёмки.**
