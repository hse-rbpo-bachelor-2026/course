# Учебный кейс: модель угроз для сервиса бронирования оборудования

Это третья часть сквозного **Lab Booking**. Контекст S01 развивается в модель угроз; [правила продукта и упражнение S02](../S02/requirements-case.md) остаются входом для анализа.

На S03 он используется, чтобы научиться строить **компактную модель угроз конкретного программного продукта**: понять, что именно защищается, где проходят границы доверия, какие угрозы действительно релевантны и какие из них важнее остальных.

В разделе 10 есть один калибровочный пример угрозы для общего разбора. Остальные сценарии команда формулирует самостоятельно; полного готового набора нет.

**С чего начать.** Откройте свои учебные заметки S02: требования `SR-*`, критерии приёмки и допущения. Если заметок нет, в начале занятия с преподавателем восстановите хотя бы одно требование и критерий по правилам S02 и согласуйте его локальный ID. Этого достаточно, чтобы начать общий разбор; по мере работы добавляйте нужные требования, не угадывая чужие номера. Самостоятельно проходить будущие задания заранее не нужно.

Для собственного проекта используются его требования из репозитория, а не учебные SR Lab Booking.

## 1. Контекст продукта

Учебная лаборатория выдаёт студентам оборудование для самостоятельной работы.

Сервис позволяет:

- студентам просматривать оборудование;
- создавать бронирования;
- просматривать и отменять собственные бронирования;
- сотрудникам лаборатории изменять состояние оборудования;
- сотрудникам лаборатории отменять бронирования при необходимости.

На S02 для продукта уже были сформулированы требования безопасности.

## 2. Основные объекты

### Оборудование

Для устройства хранятся:

- идентификатор;
- название;
- тип;
- состояние.

Примеры состояний:

- `available`;
- `maintenance`;
- `retired`.

### Бронирование

Для бронирования хранятся:

- идентификатор;
- оборудование;
- владелец;
- начало;
- окончание;
- состояние.

### Пользователь

Для учебного кейса достаточно:

- идентификатора;
- роли.

Реальные персональные данные не используются.

## 3. Архитектура

Используется простая архитектура:

```text
пользователь
    │
    ▼
Web-клиент / API-клиент
    │
    │ HTTPS
    ▼
Сервер приложения / API
    │
    ▼
База данных
```

Сервер приложения отвечает за:

- проверку входных данных;
- проверку полномочий;
- предметную логику;
- чтение и изменение состояния;
- обращение к базе данных.

## 4. Граница доверия

Главная граница доверия:

```text
клиент → сервер приложения
```

Клиентская сторона считается недоверенной.

Это означает, что сервер не должен автоматически доверять значениям, которые пришли от клиента, даже если пользовательский интерфейс обычно не позволяет их вводить.

Для модели кейса принимаем допущение: подлинность пользователя уже установлена, а сервер получает из доверенного контекста:

- идентификатор текущего пользователя;
- его роль.

Клиент не определяет их обычным параметром запроса. Это граница рассматриваемого учебного объекта, а не доказательство того, что все действия разрешены правильно. Способ установления подлинности в этом упражнении не проектируется; допустимость конкретной операции ещё нужно анализировать.

## 5. Точки входа

Для анализа используйте следующий условный API:

```text
GET    /equipment
GET    /equipment/{id}
POST   /reservations
GET    /reservations/my
DELETE /reservations/{id}

PATCH  /equipment/{id}/status
DELETE /staff/reservations/{id}
```

Точные URL для учебного анализа несущественны.

Важно понять:

- какие операции доступны;
- какие данные входят в запрос;
- какое состояние может измениться;
- какие проверки должен выполнить сервер.

## 6. Пример входных данных

Создание бронирования:

```json
{
  "equipmentId": "eq-17",
  "startAt": "2026-09-15T12:00:00Z",
  "endAt": "2026-09-15T14:00:00Z"
}
```

Отмена бронирования:

```text
DELETE /reservations/r-104
```

Изменение состояния оборудования:

```json
{
  "status": "maintenance"
}
```

Причина служебной отмены:

```json
{
  "reason": "equipment required for maintenance"
}
```

## 7. Что считать недоверенным вводом

К недоверенным данным относятся, например:

- `equipmentId`;
- `reservationId`;
- `startAt`;
- `endAt`;
- `status`;
- `reason`;
- другие параметры, поступающие от клиента.

Важно:

> корректный синтаксис значения ещё не означает, что действие допустимо.

Проверяйте смысл параметра в контексте действия, состояния продукта и полномочий пользователя; одного корректного формата недостаточно.

## 8. Задание 1. Определите, что имеет значение

Для продукта выделите объекты и свойства, нарушение которых действительно важно.

Не составляйте длинный универсальный список.

Начните с вопросов:

- что нельзя позволить изменить произвольно;
- к каким данным нельзя давать лишний доступ;
- какое состояние системы должно оставаться согласованным;
- какие полномочия нельзя подменить;
- какие действия должны оставаться доступными законному пользователю.

## 9. Задание 2. Проведите границы доверия

На схеме продукта отметьте:

- где находится недоверенная сторона;
- где начинается серверный контур;
- какие данные пересекают границу;
- какие решения сервер обязан принимать самостоятельно.

Для этого кейса достаточно одной основной границы доверия.

Не нужно усложнять схему микросервисами, внутренними сетевыми зонами и внешними системами, которых в продукте нет.

## 10. Задание 3. От примера к самостоятельным угрозам

**Вместе с преподавателем** разберите один пример:

> Обычный студент подставляет идентификатор чужого бронирования в запрос отмены и пытается изменить его состояние.

Назовите действующего субъекта, вход, затронутый объект, нарушаемое свойство и связанное SR из ваших заметок. Объясните, чем эта запись конкретнее названия «несанкционированный доступ». Это калибровка формы, а не самостоятельный результат команды.

**Затем самостоятельно** выберите другие основные сценарии и найдите способы нарушения свойств. Для поиска можно менять значения входа, порядок и сочетание действий, состояние объекта или полномочия участника. Обоснуйте, почему сценарий реалистичен для этой архитектуры, и свяжите его с SR. Хотя бы один разбираемый самостоятельно сценарий должен отличаться по смыслу от подстановки чужого идентификатора; переименование операции не считается переносом метода.

Сохраняйте несколько содержательных учебных записей; исчерпывающий каталог атак не требуется.

## 11. Задание 4. Назначьте идентификаторы

Используйте устойчивые идентификаторы:

```text
T-01
T-02
T-03
...
```

Идентификаторы понадобятся на S04 для связей с:

- требованиями `SR-*`;
- проектными решениями;
- будущими проверками.

## 12. Задание 5. Свяжите угрозы с требованиями

Для каждой угрозы найдите одно или несколько требований S02, которые описывают свойство, нарушаемое этой угрозой.

Укажите ID из своих учебных заметок и проверьте смысл связи: угроза должна описывать нарушение свойства именно этого требования. Одинаковая нумерация с другой командой или преподавателем не требуется.

Если для релевантной угрозы подходящего требования нет, это сигнал пересмотреть набор требований.

Не нужно создавать отдельный документ трассировки.

## 13. Задание 6. Определите приоритет

Для каждой угрозы оцените хотя бы:

- насколько серьёзны последствия;
- насколько реалистичен сценарий;
- относится ли он к основным сценариям продукта;
- требуется ли решение уже в текущей архитектуре.

Используйте простой приоритет:

```text
высокий
средний
низкий
```

или эквивалентную понятную шкалу.

Не требуется рассчитывать формальный числовой риск.

После анализа выделите несколько угроз, которые действительно должны влиять на проектные решения.

## 14. Вопросы для общего разбора

Подготовьтесь коротко объяснить:

1. Почему существующий идентификатор объекта всё равно может быть недоверенным вводом?
2. Чем угроза отличается от требования безопасности?
3. Почему скрытая кнопка в интерфейсе не устраняет угрозу прямого вызова API?
4. Может ли угроза появиться из двух корректных запросов?
5. Зачем связывать угрозу с уже существующим требованием?
6. Почему не нужно включать в модель все известные классы атак?

## 15. Что сохранить для S04

В тех же учебных заметках сохраните свои `T-*`, обоснованные приоритеты и связи с `SR-*`. При изменении требования уточните его формулировку и критерий приёмки. Эти заметки используются для общего упражнения на S04 и отдельно не оцениваются. Новый документ или репозиторий Lab Booking не требуется.

## 16. Что пока не требуется

На S03 не нужно:

- выбирать конкретные механизмы защиты;
- писать проектные решения;
- строить окончательную архитектуру продукта;
- перечислять все угрозы из OWASP, STRIDE или других каталогов;
- рассчитывать сложную количественную модель риска;
- создавать отдельный документ трассировки;
- создавать `CONTRIBUTIONS.md`;
- писать код специально для учебного кейса.

Сейчас задача:

> **построить компактную модель конкретного продукта, выделить релевантные угрозы и понять, какие из них должны повлиять на дальнейшие проектные решения.**
