# Учебный кейс: проектные решения безопасности

Это четвёртая часть сквозного **Lab Booking**. Входы — [предметные правила и требования S02](../S02/requirements-case.md), [архитектура и анализ угроз S03](../S03/threat-model-case.md) и ваши рабочие заметки по этим упражнениям.

На S04 вы работаете с уже знакомым сервисом бронирования оборудования и учитесь принимать **проектные решения безопасности**, которые следуют из требований и приоритетных угроз.

Ситуация A — общий калибровочный разбор. Ситуации B–D предназначены для самостоятельного применения метода; выберите одну из них после A. Полный письменный разбор всех ситуаций не требуется.

**Если учебных заметок нет:** в начале занятия вместе с преподавателем выберите одну ситуацию ниже, восстановите её предметное правило по S02, сформулируйте SR с критерием приёмки и соответствующую T по модели S03. Используйте собственные локальные ID. Это восстановление уже введённых методов; оно позволяет начать разбор без отдельной предварительной домашней работы. Для следующих ситуаций дополняйте тот же набор.

Ссылки в упражнении относятся к вашему набору Lab Booking. Не нужно угадывать номера другой команды или переносить эти записи в собственный продукт.

## 1. Контекст

Сервис позволяет студентам:

- просматривать оборудование;
- создавать бронирования;
- просматривать и отменять собственные бронирования.

Сотрудник лаборатории дополнительно может:

- изменять состояние оборудования;
- отменять чужие бронирования при необходимости.

Для продукта уже существуют:

- требования безопасности `SR-*`;
- модель угроз `T-*`;
- несколько приоритетных угроз.

На S04 нужно решить, **где и как продукт будет обеспечивать нужное свойство**, а затем связать решение с угрозой, требованием и будущей проверкой.

## 2. Ситуация A. Общий разбор отмены чужого бронирования

В пользовательском интерфейсе кнопка отмены показывается только рядом с собственными бронированиями.

Разработчик предлагает считать этого достаточным:

> Пользователь всё равно не видит кнопку для чужого бронирования.

При этом API содержит операцию:

```text
DELETE /reservations/{id}
```

### Обсудите

1. Устраняет ли скрытая кнопка угрозу управления чужим бронированием?
2. Где должно приниматься окончательное решение о допустимости операции?
3. Какие данные нужны серверу для такого решения?
4. Какую будущую проверку можно выполнить?
5. С каким `SR-*` и `T-*` должно быть связано решение?

После обсуждения сравните с калибровочным выводом: сервер перед отменой получает пользователя из доверенного контекста, определяет владельца целевого бронирования и проверяет право на операцию. Для обычного студента изменение чужого бронирования отклоняется без изменения состояния; допустимая отмена своего бронирования выполняется по правилам продукта. В свёрнутом виде это основа D; добавьте связи с вашими SR/T и обоснование. Будущая проверка разобрана в разделе 7.

Этот пример служит опорой для самостоятельной работы над другой ситуацией.

## 3. Ситуация B. Пересекающиеся бронирования

При создании бронирования сервер выполняет:

```text
1. проверить, свободен ли интервал;
2. если свободен — создать бронирование.
```

Оба действия выполняются отдельными запросами к базе данных.

Разработчик считает:

> Проверка есть, значит два пересекающихся бронирования создать нельзя.

### Обсудите

1. Что произойдёт, если два запроса выполняются почти одновременно?
2. Может ли каждый запрос увидеть свободный интервал?
3. Какое свойство должно гарантировать выбранное решение?
4. Достаточно ли проверки только на уровне пользовательского интерфейса?
5. Как можно будет проверить решение конкурентным сценарием?

Сформулируйте проектное решение, не привязываясь без необходимости к конкретной СУБД.

## 4. Ситуация C. Изменившееся состояние оборудования

При открытии формы оборудование было доступно. Пока студент выбирал время, сотрудник перевёл его в `maintenance`. Запрос на бронирование поступает после этого; ранее показанное состояние уже устарело.

### Обсудите

1. Какое требование S02 относится к этому случаю?
2. Какое состояние важно для решения и в какой момент оно должно учитываться?
3. Какие изменения могут произойти между наблюдением состояния и созданием бронирования?
4. Какую гарантию должно обеспечить выбранное решение?
5. Какие условия и порядок действий нужны будущей проверке?

Сформулируйте решение с обоснованием и существенными допущениями; повторения «скрыть кнопку» или «проверить владельца» недостаточно.

## 5. Ситуация D. Прослеживаемость служебной отмены

По правилам S02 сотрудник может отменить чужое бронирование с указанием причины. После действия должно быть возможно установить исполнителя, бронирование, время и причину. Это уже заданное свойство; на S04 выбирается способ его обеспечения.

Разработчик предлагает двумя независимыми действиями изменить состояние на `cancelled` и сохранить сведения об отмене. Между ними может возникнуть сбой.

### Обсудите

1. Какие неполные результаты возможны при таком порядке действий?
2. Откуда должны браться исполнитель и время, какие сведения передаёт клиент?
3. Какую согласованность состояния и сведений об отмене должно обеспечить решение?
4. Как подтвердить её проверкой, учитывающей сбой?
5. Какие ограничения и допущения есть у выбранного способа? Можно ли обеспечить требуемое свойство без большой системы журналирования?

Сформулируйте решение подходящего масштаба и будущую проверку. Не заменяйте инженерный выбор повторением перечня полей из S02.

## 6. Что должно содержать проектное решение

Для каждого выбранного случая зафиксируйте:

- устойчивый идентификатор `D-*`;
- проблему или контекст;
- принятое решение;
- почему оно выбрано;
- связанные требования `SR-*`;
- связанные угрозы `T-*`;
- будущую проверку;
- существенные ограничения или последствия решения, если они есть.

Не требуется писать длинный архитектурный документ.

Одно хорошее решение может занимать несколько коротких абзацев.

## 7. Что значит «будущая проверка»

На S04 не нужно обязательно реализовать саму проверку.

Нужно понять, **каким наблюдаемым действием позже можно подтвердить решение**. Сошлитесь на критерий приёмки соответствующего SR и уточните условия проверки выбранного механизма. Если ожидаемый результат уже указан в критерии, повторять его дословно не требуется. Записанный сценарий ещё не является фактическим свидетельством.

Пример для уже разобранной ситуации A:

```text
обычный студент пытается отменить чужое бронирование
→ сервер отказывает
→ состояние бронирования не меняется
```

Дополните проверку допустимой отменой собственного бронирования по правилам продукта. Для выбранной ситуации B, C или D сформулируйте условия и ожидаемый результат самостоятельно; этот пример не является готовой проверкой для них.

Не пишите просто:

> Проверить авторизацию.

Нужен конкретный сценарий и ожидаемый результат.

## 8. Задание

Ситуацию A разберите вместе с преподавателем, затем самостоятельно или в команде примените метод к одной из ситуаций B–D. Дополнительные ситуации можно использовать для обсуждения; полный письменный разбор всех четырёх не требуется.

Для каждой:

1. найдите связанное требование;
2. найдите связанную приоритетную угрозу;
3. сформулируйте проектное решение;
4. объясните, почему оно должно работать;
5. определите будущую проверку;
6. назначьте `D-*`.

Затем перейдите к собственному продукту по README S04. Учебные заметки Lab Booking можно сохранить для себя; отдельная сдача, репозиторий или отчёт по этому кейсу не нужны.

После этого убедитесь, что для решения видна цепочка:

```text
T-* → SR-* → D-* → будущая проверка
```

Отдельный документ только ради этой цепочки не создаётся.

## 9. Вопросы для общего разбора

Подготовьтесь коротко объяснить:

1. Чем проектное решение отличается от требования безопасности?
2. Почему «скрыть кнопку» обычно не является достаточным решением для серверного ограничения?
3. Почему предварительная проверка состояния может быть недостаточной?
4. Когда технология является частью решения, а когда — лишней детализацией?
5. Почему будущую проверку полезно определить до реализации?
6. Какие ограничения или компромиссы может создавать выбранное решение?

## 10. Что пока не требуется

Для учебного кейса S04 не нужно:

- реализовывать решения в коде;
- выбирать все технологии окончательно;
- строить отдельный документ трассировки;
- описывать решение для каждой угрозы;
- писать десятки архитектурных записей;
- создавать полный журнал событий;
- подключать автоматизированные анализаторы.

Сейчас задача:

> **для нескольких приоритетных угроз принять конкретные инженерные решения и показать, как они связаны с уже существующими требованиями и будущими проверками.**
